## ראיות לשינויים הקיימים — עובדה מול המלצה

### Ollama

[API Introduction](https://docs.ollama.com/api/introduction) נפתח ומבחין בין direct cloud לבין שרת מקומי, ומציג ספריות רשמיות Python/JavaScript; אינו מאמת SDK C# רשמי. [Authentication](https://docs.ollama.com/api/authentication) קובע שה־local API אינו דורש אימות כברירת מחדל, ושאפשר לקרוא מודל cloud דרך local API לאחר כניסה. לכן **localhost אינו הוכחה שה־prompt נשאר במחשב**. [FAQ](https://docs.ollama.com/faq) מתעד local-only באמצעות disable_ollama_cloud או OLLAMA_NO_CLOUD והגבלת ברירת המחדל ל־127.0.0.1. זו אפשרות תצורה לבדיקה, לא הבטחת פרטיות לכל MCP/tool חיצוני.

[רישיון הקוד](https://github.com/ollama/ollama/blob/main/LICENSE) MIT; רישיון כל מודל ושירות הענן נפרדים. המלצה: דוגמה של ASP.NET adapter שמקבל endpoint/model ממדיניות שרת, בודק פלט ומגביל בקשות. יתרון: פשטות התחלה; חסרון: מתאם API, model tags ותפעול אינם מחליפים הרשאות ובדיקות. תאריך השקה ראשון לא אומת; לא למלא אותו משנת יצירת GitHub.

### LM Studio

[Developer Docs](https://lmstudio.ai/docs/developer) מאמת SDK Python ו־TypeScript וגם llmster daemon עצמאי שאינו תלוי ב־GUI. יש native REST לצד compatibility endpoints; אלה ממשקים שונים עם כיסוי תכונות שונה. C# יכול להשתמש ב־HTTP, אך אין בדוח הוכחת SDK C# רשמי. [Authentication](https://lmstudio.ai/docs/developer/core/authentication) מציין תמיכת API Tokens מ־0.4.0; ברירת המחדל אינה דורשת token, ולכן בפריסה לרשת חייבים לבדוק הגדרות ולא להניח auth.

[Offline](https://lmstudio.ai/docs/app/offline) מתאר שימוש מקומי במודלים שכבר הורדו, בעוד חיפוש/הורדה ועדכון runtimes דורשים רשת. [System requirements](https://lmstudio.ai/docs/app/system-requirements) מפריד OS/CPU/חומרה; אין הבטחה שכל מודל יתאים ל־16GB. יתרון: מעבר קצר מממשק לניסוי API; חסרון: תלות באפליקציה/engine/model ותנאי רישיון, ולא פלטפורמה חופשית רק מפני שהיא חינם.

[Changelog LM Studio](https://lmstudio.ai/changelog/lmstudio) מציג0.4.28 מ־31/10/2026. דף /changelog ברירת המחדל מציג Bionic, מוצר סמוך; אין להסיק מכך שינוי שם או הפסקת LM Studio. [תנאים נוכחיים](https://lmstudio.ai/app-terms) מתוארכים23/08/2026, ו־[free-for-work](https://lmstudio.ai/blog/free-for-work) מ־08/07/2025 מסיר דרישת פנייה לרישיון מסחרי לשימוש רגיל בעבודה. זה אינו רישיון קוד פתוח ליישום. אותו פוסט מאשר השקה במאי2023; שנה בלבד נשמרת עד יום מאומת.

### llama.cpp

[Server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md) מאמת שרת C/C++ עם APIs, continuous batching, structured JSON, ויכולות model-dependent. המנוע שונה ממשפחת Llama של Meta, ושימוש HTTP אינו binding C# מקומי. [MIT](https://github.com/ggml-org/llama.cpp/blob/master/LICENSE) מתייחס לקוד, לא למשקלים. הצעה: להרחיב ניסוי כימות עם דגם ומשימה קבועים ומדידות זיכרון/זמן/איכות; אין הנחה שכימות תמיד מהיר יותר או שעברית נבדקה. [v0.8.0](https://github.com/ggml-org/llama.cpp/releases/tag/v0.8.0) מ־28/10/2026 הוא אירוע עדכון, לא השקה. [Initial release commit](https://github.com/ggml-org/llama.cpp/commit/26c084662903ddaca19bef982831bfb0856e8257) נפתח ותווית Initial release אושרה; תאריך10/03/2023 בבסיס אינו תאריך יצירת מאגר, ואין הצעת שינוי שלו.

### vLLM

[תיעוד רשמי](https://docs.vllm.ai/en/latest/) מפריד offline/online serving, סוגי חומרה ותכונות. אין להציג vLLM ככלי NVIDIA-only באופן גורף או כהבטחת תמיכה native ב־Windows; יש לבדוק את backend ומדריך החומרה הספציפי. [Security](https://docs.vllm.ai/en/latest/usage/security/) מזהיר ש־--api-key מגן רק על prefixes מוגדרים, ו־endpoints רגישים אחרים עשויים להישאר ללא אכיפת auth. המלצה: gateway/firewall/reverse proxy, ולא טענה שדגל key לבדו סוגר production.

[הכרזה20/06/2023](https://vllm-project.github.io/2023/06/20/vllm.html) מאמתת השקה ציבורית ונבדלת משימוש פנימי מוקדם. [Apache2](https://github.com/vllm-project/vllm/blob/main/LICENSE) מתייחס לקוד. [ה־release האחרון שנמדד](https://github.com/vllm-project/vllm/releases/tag/v0.33.0rc3) נקרא בכותרת v0.33.0 אך tag הוא v0.33.0rc3 וה־API מחזיר prerelease=false. הסתירה נשמרת: **אין לכנותו stable אוטומטית**; לפני POC צריך pinning לגרסה/artefact שנבחרו ובדיקת release notes. דוגמה מוצעת: שרת ASP.NET מווסת עומס והסקה נפרדת, עם TTFT, tokens/sec, p95, כשלים וזיכרון — לא רק קצב ממוצע.

## תוספות מומלצות: תפקיד, שפות, רישוי ותרחיש

**LiteLLM (I08-06):** [AI Gateway](https://docs.litellm.ai/docs/simple_proxy) הוא שרת self-host שנותב לספק/שרת המודל ומרכז virtual keys, budgets, retries, fallbacks וניטור. [מבוא](https://docs.litellm.ai/docs/) מפריד Python SDK מהמוצר gateway. .NET/TypeScript יכולים לצרוך HTTP; אין לתייג את Python SDK כ־SDK C# או להבטיח parity לכל endpoint. [LICENSE](https://github.com/BerriAI/litellm/blob/main/LICENSE) מציין MIT מחוץ ל־enterprise/ ורישיון נפרד לתיקייה זו; יש לבדוק תכונה ו־edition לפני הבטחת SSO או control מסוים. שימוש מוצע: ASP.NET→gateway→Ollama מקומי או ספק שאושר. יתרון: מדיניות במקום אחד; חסרון: hop, DB/לוגים ותפעול נוספים, ו־fallback עשוי לשנות נתיב מידע. השקה ראשונה לא אומתה.

**ONNX Runtime GenAI (I08-07):** [Generate API](https://onnxruntime.ai/docs/genai/), [C# API](https://onnxruntime.ai/docs/genai/api/csharp.html) ו־[README](https://github.com/microsoft/onnxruntime-genai) נפתחו. C# רשמי להפעלה בתוך התהליך, לצד Python/C/C++; generate API מסומן **Preview**. [Install](https://onnxruntime.ai/docs/genai/howto/install.html) מחייב התאמה בין package, model, execution provider ופלטפורמה; ONNX Runtime הרגיל אינו זהה לשכבת GenAI. [MIT](https://github.com/microsoft/onnxruntime-genai/blob/main/LICENSE) אינו רישיון המודל. תרחיש מוצע: חילוץ שדות מפתק שירות באפליקציית .NET offline עם מודל ONNX נתמך. יתרון: בלי שרת HTTP הכרחי; חסרון: packaging/model conversion, זיכרון ו־Preview API. לא אותרה הוכחה ל־GA או לשוויון יכולות בכל EP; יום השקה ראשונה לא אומת.

**SGLang (I08-08):** [README](https://github.com/sgl-project/sglang), [Quickstart](https://docs.sglang.io/docs/get-started/quickstart), [Installation](https://docs.sglang.io/docs/get-started/install) ו־[Apache2](https://github.com/sgl-project/sglang/blob/main/LICENSE) נפתחו. זהו מנוע/framework serving, עם Python ו־HTTP ללקוחות .NET; אין SDK C# native מאומת. מדריך ההתחלה הנוכחי ממוקד Linux/NVIDIA/CUDA13; README כולל backends נוספים בעלי מסלולים משלהם. אין להסיק זמינות אחידה מכל רשימת חומרה. דוגמה מוצעת: להשוות vLLM ו־SGLang על אותו מודל, חומרה ופרופיל בקשות. יתרון: חלופה רלוונטית להבנת serving/caching; חסרון: סביבת GPU ותלויות כבדות. יום השקה ראשון לא אומת ואין טענת מהירות יחסית ללא benchmark משותף.

## מדריך, יתרונות/חסרונות ותרגיל מוצעים

הסדר המומלץ: יסודות → Ollama או LM Studio → llama.cpp → בחירת in-process .NET באמצעות ONNX Runtime GenAI **או** שרת בקשות vLLM/SGLang → gateway LiteLLM כאשר ריבוי endpoints/teams מצדיק אותו. להשאיר כלים כתפקידי should_know, לא להפוך את כולם לחובה. יסודות הם must_learn משום שהם מלמדים להשוות תוצאות ולבדוק גבולות.

תרגיל מעשי מוצע שלא הורץ: React→ASP.NET endpoint עם DTO מוגדר→שרת inference מקומי. המשימה היא חילוץ מספר הזמנה, תאריך וקטגוריית פנייה מטקסט דוגמה. שמרו מודל/פורמט/כימות/חומרה/קלט/אורך פלט קבועים; מדדו זמן טעינה, TTFT, קצב, p95, שגיאות וזיכרון ובדקו איכות תוכן. רק לאחר baseline הוסיפו concurrency או gateway. אם נדרש offline מלא, בדקו גם tools, הורדות, טלמטריה ו־fallback, ולא רק כתובת HTTP.
